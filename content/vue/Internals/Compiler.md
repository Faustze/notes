# Compiler: template → render function → vdom

> **Цель этого конспекта** — разобраться, как Vue 3 превращает шаблон (`.vue`) в **рендер-функцию**, которая порождает **виртуальный DOM (VNode)**, и как этот VNode в итоге обновляет реальный DOM.

Весь процесс проходит через **компилятор** — модуль, который работает **на этапе сборки** (если используется `vue-loader` / `@vue/compiler-sfc`) или **в браузере** (при использовании `vue.global.js` с компиляцией на лету).

---
### QUICK REMINDER

**Vue компилирует шаблон в JavaScript-функцию (`render`),**  
**которая при каждом вызове возвращает VNode-дерево.**  
**Рендерер (patch) сравнивает новое и старое дерево и обновляет DOM только там, где это необходимо.**

- Компилятор работает **статически** (анализирует шаблон до выполнения).
- Оптимизации: статический подъём, патч-флаги, блочное дерево.
- В рантайме используется только **рендерер** — он ничего не знает о шаблоне, только о VNode.

---
## Общая картина

```text
        Шаблон (template)
                │
                ▼
         Парсинг (Parser)
                │
                ▼
   AST (Abstract Syntax Tree)
                │
                ▼
  Трансформации (Transform)
                │
                ▼
   Оптимизированный AST
                │
                ▼
   Генерация кода (Codegen)
                │
                ▼
     Рендер-функция (render)
                │
                ▼
   Вызов render() → VNode-дерево
                │
                ▼
   Пэтчинг (patch) → реальный DOM
```

**Важно:** Vue 3 использует **компилятор на основе AST**, который полностью переписан по сравнению с Vue 2. Он **независим от рантайма**, что позволяет выполнять компиляцию как на сервере, так и на клиенте.

---
# 1. Парсинг шаблона

На входе — строка шаблона:

```html
<div id="app">
  <p>{{ message }}</p>
  <button @click="handleClick">Click</button>
</div>
```

Парсер (на основе конечного автомата) разбивает строку на **токены** и строит **AST** (Abstract Syntax Tree) — дерево, отражающее структуру.

Каждый узел AST содержит:

- `type` (Element, Text, Interpolation, Directive, …)
- `tag` (для элементов)
- `props` (атрибуты, директивы, события)
- `children` (вложенные узлы)
- `loc` (информация о позиции в исходном коде)

Пример AST (упрощённо):

```js
{
  type: 'Root',
  children: [
    {
      type: 'Element',
      tag: 'div',
      props: [
        { type: 'Attribute', name: 'id', value: 'app' }
      ],
      children: [
        {
          type: 'Element',
          tag: 'p',
          children: [
            {
              type: 'Interpolation',
              content: { type: 'Expression', content: 'message' }
            }
          ]
        },
        {
          type: 'Element',
          tag: 'button',
          props: [
            {
              type: 'Directive',
              name: 'on',
              arg: 'click',
              exp: { type: 'Expression', content: 'handleClick' }
            }
          ],
          children: [
            { type: 'Text', content: 'Click' }
          ]
        }
      ]
    }
  ]
}
```

Парсер обрабатывает все синтаксические конструкции: `v-if`, `v-for`, `v-model`, слоты, динамические аргументы, модификаторы и т.д.

---
# 2. Трансформации AST

Исходный AST содержит только синтаксическую структуру. Чтобы его можно было превратить в эффективный код, выполняются **трансформации**.

## 2.1. Преобразование директив

- `v-if` → превращается в тернарный оператор или условный рендеринг.
- `v-for` → превращается в вызов `_l()` (или `renderList`).
- `v-model` → раскрывается в привязку `value` и событие `input` / `update:modelValue`.
- `v-on` → преобразуется в слушатели событий (`_on`).
- `v-bind` → преобразуется в объект атрибутов.

## 2.2. Анализ и оптимизация

Vue 3 вводит понятие **блочного дерева** (Block Tree) и **патч-флагов** (Patch Flags). На этапе трансформации компилятор помечает узлы, которые могут динамически меняться:

- `TEXT` – текст может измениться.
- `CLASS` – класс может измениться.
- `STYLE` – стиль может измениться.
- `PROPS` – другие атрибуты могут измениться.
- `FULL_PROPS` – всё может измениться (сложный случай).

Также выполняется **статический подъём** (hoisting): статические узлы (не содержащие реактивных привязок) выносятся за пределы рендер-функции, чтобы не создаваться заново при каждом перерендере.

```text
Пример подъёма:
  статичный <div class="static"> → выносится в константу вне render()
```

## 2.3. Генерация дерева блоков

Для ускорения патчинга Vue 3 строит **блоки** — узлы, которые имеют динамические дочерние элементы. Внутри блока все динамические узлы собираются в массив, что позволяет при обновлении обходить только их, а не всё дерево целиком.

---
# 3. Генерация кода (Codegen)

На основе оптимизированного AST генерируется **рендер-функция** — обычный JavaScript-код, который возвращает VNode-дерево.

Генератор использует вспомогательные функции, доступные в рантайме (импортируемые из `vue`):

- `_createElementVNode` (или `h` для ручного использования)
- `_createElementBlock` – для блоков
- `_createCommentVNode`, `_createTextVNode`
- `_renderList` (для `v-for`)
- `_renderSlot` (для слотов)
- `_withDirectives` (для директив)
- `_withModifiers` (для модификаторов событий)

Пример сгенерированной рендер-функции для предыдущего шаблона:

```js
import { createElementBlock, createElementVNode, toDisplayString } from 'vue'

export function render(_ctx, _cache) {
  return createElementBlock('div', { id: 'app' }, [
    createElementVNode('p', null, [
      createElementVNode(
        'text',
        null,
        toDisplayString(_ctx.message),
        1 /* TEXT patch flag */
      )
    ]),
    createElementVNode(
      'button',
      { onClick: _ctx.handleClick },
      'Click'
    )
  ])
}
```

Обратите внимание:

- `_ctx` – контекст (прокси к данным компонента, содержащий все свойства, методы, computed, инъекции и т.д.).
- `_cache` – кэш для статических узлов, поднятых вверх (если есть).
- `toDisplayString` – функция, преобразующая значение в строку (экранирует).
- `1` – это патч-флаг для текстового узла.

---
# 4. Рендер-функция → VNode

Когда компонент монтируется или обновляется, вызывается его `render()` (либо скомпилированная, либо написанная вручную). Она возвращает **VNode** – виртуальный узел, который описывает DOM-элемент или компонент.

VNode – это простой объект с полями:

- `type` – тег (строка) или компонент (объект)
- `props` – объект атрибутов/свойств
- `children` – массив дочерних VNode или текст
- `key` – уникальный идентификатор (для эффективного diff)
- `patchFlag` – битовая маска, указывающая, какие части VNode могут измениться
- `dynamicChildren` – массив только динамических дочерних узлов (если блок)
- и другие служебные поля (`el`, `component`, `shapeFlag` и т.д.)

**Важно:** VNode – это не DOM-элемент. Это **лёгкое представление** того, что должно быть на странице.

---
# 5. VNode → Реальный DOM (Патчинг)

Процесс превращения VNode в DOM и последующего обновления называется **патчингом** и выполняется функцией `renderer` (рендерер).

## 5.1. Монтирование (mount)

При первом рендере:

1. Создаются реальные DOM-элементы на основе VNode.
2. Устанавливаются атрибуты, слушатели событий.
3. Дочерние VNode рекурсивно монтируются.
4. Созданный DOM вставляется в контейнер (`app.mount('#app')`).

## 5.2. Обновление (patch)

При повторном рендере (из-за изменения реактивных данных):

1. Вызывается `render()` → получаем новый VNode.
2. Рендерер сравнивает новый VNode со старым (который был сохранён при предыдущем рендере).
3. Алгоритм **diff** (на основе `key`, `type`, `patchFlag`) определяет минимальные изменения.
4. Изменения применяются к реальному DOM (обновление текста, атрибутов, добавление/удаление элементов).

### Блочный diff

Благодаря `patchFlag` и `dynamicChildren`, Vue 3 может пропускать целые статические участки. Для блока (элемента с `patchFlag` > 0) он знает, какие дети динамичны, и перебирает только их, не трогая статику.

### Ключи (key)

Для списков с `v-for` важно задавать уникальный `key`, чтобы diff мог эффективно перемещать элементы, а не пересоздавать их.

# 6. Роль компилятора в разных сценариях

## 6.1. Сборка с помощью Vite / Webpack (рекомендуемый способ)

- Шаблоны компилируются на этапе сборки.
- На выходе – `render` функция (импорты из `vue`).
- Браузер получает уже готовый JavaScript.
- Это быстрее и экономит трафик.

## 6.2. Компиляция в браузере (runtime + compiler)

- При использовании `vue.global.js` или `@vue/compiler-dom` отдельно.
- Шаблоны компилируются в момент запуска приложения.
- Медленнее, но удобно для прототипирования.

## 6.3. Серверный рендеринг (SSR)

- Компилятор также генерирует специальную `ssrRender` функцию.
- Вместо создания VNode, она напрямую генерирует строку HTML (более производительно).

# 7. Внутреннее устройство компилятора (кратко)

```text
@vue/compiler-core
   │
   ├── parser (parse.ts)
   │    └── токенизация, построение AST
   │
   ├── transform (transform.ts)
   │    ├── применяет плагины трансформации
   │    ├── анализирует реактивность
   │    └── строит оптимизированное AST
   │
   ├── codegen (codegen.ts)
   │    └── генерирует JavaScript-код
   │
   └── runtime-helpers (runtimeHelpers.ts)
        └── набор функций, используемых в сгенерированном коде
```

`@vue/compiler-dom` добавляет специфичные для DOM трансформации (атрибуты, события), а `@vue/compiler-sfc` работает с однофайловыми компонентами (извлекает `<script>`, `<style>`, `<template>`).

---
# 8. Почему это важно понимать?

- **Оптимизация производительности** – знание, как компилятор обрабатывает шаблоны, помогает избегать лишних перерендеров (например, не помещать большие статические блоки внутрь динамических участков).
- **Понимание ошибок** – если вы видите ошибку "render function is not a function", вы знаете, что компиляция не удалась.
- **Возможность писать кастомные трансформации** – в сложных проектах можно расширить компилятор своими плагинами (например, для поддержки новых атрибутов).
- **Осознание различий между `template` и `render`** – обе формы в итоге дают один и тот же результат, но `render` даёт больше контроля и гибкости (ценой удобства).

## Формула компиляции

```text
template   →   AST   →   оптимизированный AST   →   render функция   →   VNode   →   patch   →   DOM
```

> **Ключевая мысль:** Vue компилирует шаблон в **JavaScript-функцию**, которая при каждом вызове создаёт **виртуальное DOM-дерево**. Затем рендерер сравнивает новое и старое дерево и эффективно обновляет реальный DOM. Компилятор делает это максимально быстро, используя статический анализ и патч-флаги.

## 1. Зачем вообще нужна render-функция?

| Шаблон (template) | Render-функция (JS) |
|-------------------|----------------------|
| Удобен для человека | Нужен для машины (JS-движок) |
| Декларативный | Императивный (можно писать любую логику) |
| Компилируется в render | Выполняется напрямую |

**Вывод:** Vue превращает шаблон в render-функцию, потому что JavaScript-функции выполняются быстрее (компилируются в машинный код) и дают полную гибкость.

---
## 2. Этапы компиляции (от строки до DOM)

```mermaid
flowchart LR
    A[Шаблон (строка)] --> B[Парсер]
    B --> C[AST]
    C --> D[Трансформации]
    D --> E[Генерация кода]
    E --> F[render-функция]
    F --> G[VNode-дерево]
    G --> H[Патчинг (patch)]
    H --> I[DOM]
```

**Кратко о каждом этапе:**

- **Парсер** → читает строку и строит AST (дерево узлов). AST нужен компилятору для анализа.
- **Трансформации** → проход по AST, где директивы (`v-if`, `v-for`, `v-model`) заменяются на JS-код (тернарники, вызовы `renderList` и т.д.). Также добавляются оптимизации.
- **Генерация кода** → на основе AST создаётся строка JavaScript-кода (функция `render`), которая использует вспомогательные функции (например, `createElementVNode`).
- **Вызов render()** → возвращает VNode-дерево (виртуальный DOM).
- **Патчинг** → сравнивает новый VNode со старым и обновляет реальный DOM минимальным образом.

---
## 3. Что такое AST и как компилятор его «понимает»

- AST = Abstract Syntax Tree (дерево, описывающее структуру шаблона).
- Компилятор **обходит** узлы и применяет правила (плагины) для каждого типа узла.
- Пример: увидел `Interpolation` ({{ message }}) → заменяет на `toDisplayString(_ctx.message)`.

---
## 4. VNode (виртуальный узел)

- **VNode** — лёгкий объект, описывающий DOM-элемент или компонент.
- Почему VNode, а не сразу DOM? Потому что сравнивать объекты дешевле, чем работать с реальным DOM.
- **VNode-дерево** — это структура, возвращаемая render-функцией.

**Основные поля VNode:**
- `type` – тег или компонент
- `props` – атрибуты/свойства
- `children` – массив дочерних VNode или текст
- `key` – для идентификации в списках
- `patchFlag` – битовая маска изменений
- `dynamicChildren` – массив динамических потомков (для блоков)

---
## 5. Оптимизации компилятора

### 5.1. Статический подъём (hoisting)

- Статические VNode (не содержащие реактивных привязок) выносятся **за пределы render-функции** в константы.
- При каждом вызове render используется уже созданный VNode (не создаётся заново).
- Экономия памяти и времени.

**Пример:**
```js
const _hoisted_1 = createElementVNode('div', { class: 'static' }, null)

function render(_ctx) {
  return createElementBlock('div', null, [
    _hoisted_1,
    createElementVNode('p', null, toDisplayString(_ctx.count))
  ])
}
```

### 5.2. Патч-флаги (patchFlags)

- Числа, указывающие, **что именно может измениться** в этом VNode (текст, класс, стиль, атрибуты).
- При обновлении рендерер проверяет только эти части, не углубляясь во всё дерево.
- Ускоряет diff.

### 5.3. Блоки и dynamicChildren

- **Блок** — узел, который содержит массив `dynamicChildren` (только динамические дочерние VNode).
- При обновлении рендерер перебирает только `dynamicChildren`, игнорируя статику внутри блока.
- Это позволяет пропускать целые статические участки.

---
## 6. Реактивность v-for и патчинг списков

- `v-for` **сам не реактивен**. Реактивны данные (массив).
- При изменении массива `trigger` перезапускает render-функцию компонента.
- Внутри render вызывается `renderList` (простой цикл), который создаёт массив новых VNode из текущих данных.
- **patch** сравнивает новый массив VNode со старым (сохранённым) и вычисляет минимальные изменения (перемещение, удаление, добавление).
- Для этого критически важен `key` — он позволяет идентифицировать элементы при перемещении.

---
## 7. Приоритет v-if и v-for (важно!)

- `v-for` имеет **более высокий приоритет**, чем `v-if`.
- Компилятор генерирует цикл, а внутри него — тернарник с `v-if`.
- Это приводит к тому, что **все элементы** массива итерируются и для каждого создаётся VNode (или комментарий при `false`). Это неэффективно.

**Правильное решение:**
- Не использовать `v-if` и `v-for` на одном элементе.
- Либо вынести `v-if` на родительский `<template>`, либо использовать `computed` для фильтрации списка.

## 8. Пример: шаблон → render-функция

**Исходный шаблон:**
```vue
<template>
  <div>{{ message }}</div>
</template>
```

**Сгенерированная render-функция (упрощённо):**
```js
function render(_ctx) {
  return createElementBlock(
    'div',
    null,
    toDisplayString(_ctx.message),
    1 /* TEXT patch flag */
  )
}
```

## 9. Ручная render-функция (если не использовать шаблон)

Можно писать render-функции сами, используя `h` (createElement):

```js
export default {
  props: ['items'],
  render() {
    return h('ul', 
      this.items.map(item => h('li', { key: item.id }, item.name))
    )
  }
}
```

Это даёт полную гибкость, но теряет оптимизации компилятора (hoisting, патч-флаги, блоки).

## 11. Главная мысль (запомнить)

> **Vue компилирует шаблон в JavaScript-функцию, потому что JS-функции быстрее и гибче. Компилятор добавляет оптимизации (hoisting, patchFlags, блоки), чтобы рендерер (patch) мог обновлять DOM максимально эффективно, переиспользуя статику и обходя только динамические части.**
