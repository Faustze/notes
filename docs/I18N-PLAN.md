# i18n: RU/EN для заметок

Статус: реализовано. Этот файл описывает финальную архитектуру, а не хронологию решений — промежуточные варианты (Claude API по ключу, OAuth-подписка для CI и т.д.) отброшены и здесь не описываются.

## Ограничения, определившие архитектуру

- `content/` (74 md-файла) целиком перезаписывается `scripts/sync-obsidian-notes.sh` из внешнего репозитория `Faustze/Obsidian-Notes` — **редактировать нельзя**, любые правки сотрутся при следующей синхронизации.
- Контент в `content/` изначально смешан по языку: `headhunter/*` на русском, `leetcode/*` и `vue/*` на английском.
- Quartz v5 не умеет нативно в мультиязычный контент (`quartz/i18n` переводит только UI-строки интерфейса — кнопки, даты — не сами заметки).
- Раздельные URL (`/` и `/ru/`) выбраны вместо клиентского переключения контента на одной странице — ради SEO/ссылок и простоты кэширования переводов.

## Архитектура

```bash
content/           ← оригинал из Obsidian-Notes, не трогаем, эта же папка = корень сайта (EN/как есть)
content-ru/        ← переведённые заметки, зеркалирует структуру content/, закоммичена в репозиторий
  .translation-manifest.json   ← {relPath: sha256(source)} — кэш, что уже переведено
local-plugins/
  lang-switch/      ← локальный Quartz-компонент, кнопка EN/RU в сайдбаре
scripts/
  translate-content.mjs     ← переводит изменившиеся файлы content/ → content-ru/ через `claude -p`
  generate-ru-config.mjs    ← генерирует quartz.config.ru.yaml (baseUrl → .../ru)
  serve-both.mjs            ← собирает оба дерева и раздаёт локально одним сервером
.githooks/
  pre-commit         ← переводит и стейджит content-ru/ в коммит
  pre-push           ← блокирует пуш, если content-ru/ устарел
quartz/plugins/loader/config-loader.ts   ← +QUARTZ_CONFIG_PATH override (единственный патч ядра)
```

Сборка — двумя независимыми вызовами `quartz build`:

```bash
npx quartz build                          # content/    → public/     (EN, locale/baseUrl как в quartz.config.yaml)
npm run build:ru                          # content-ru/ → public/ru   (RU, baseUrl = .../ru)
```

`npm run build:ru` сначала гоняет `generate-ru-config.mjs` (копирует `quartz.config.yaml`, меняя только `configuration.baseUrl` на `<baseUrl>/ru`), затем собирает с `QUARTZ_CONFIG_PATH=quartz.config.ru.yaml`. Единственная причина отдельного конфига — `baseUrl`: Explorer/Search/Graph в Quartz строят ссылки не через relative-резолвинг (как обычные wikilinks), а через `resolveBasePath(slug)`, которая читает базовый путь из `data-basepath` (сервер вычисляет его из `baseUrl`). Без второго `baseUrl` эти три компонента при переходе с `/ru/...` всегда вели бы обратно на корень (EN) — заметка о конкретном фиксе была отдельной итерацией отладки.

Оба билда используют один и тот же `.quartz/plugins/` (устанавливается один раз через `npm run install-plugins` перед обоими) — переустановки плагинов не дублируются.

## Перевод

`scripts/translate-content.mjs`:

- обходит `content/**/*.md`, считает sha256 каждого файла;
- если хэш совпадает с записью в `content-ru/.translation-manifest.json` — файл пропускается (перевод уже есть и актуален), запрос не делается;
- иначе прогоняет содержимое через `claude -p "<промпт>"` (headless-режим CLI `claude`, авторизованного локально через `claude login`/`ant auth login`) и пишет результат в `content-ru/`;
- промпт просит сохранять код, wikilinks, LaTeX, HTML-теги и нетекстовые frontmatter-поля (`tags`, `aliases`) без изменений, переводить `title`/`description` и всю обычную прозу; уже русский текст возвращается как есть.
- удаляет из `content-ru/` файлы, для которых пропала пара в `content/` (переименование/удаление).

Важно: перевод НЕ идёт через Anthropic API (`ANTHROPIC_API_KEY`/Console) — прямые вызовы `/v1/messages`, даже с OAuth-токеном подписки, списываются с баланса API-кредитов, а не с дневных лимитов Claude-подписки. `claude -p` — это тот же процесс, что использует интерактивная Claude Code, поэтому расходуется обычная подписка.

**Автоматизация — git-хуки, не CI:**

- `.githooks/pre-commit` — если `claude` CLI установлен, переводит изменившиеся `content/*.md` и стейджит `content-ru/` в тот же коммит. Нет `claude` — тихо пропускает (коммит не блокируется, `content-ru/` может отстать).
- `.githooks/pre-push` — `translate-content.mjs --check` (без вызовов `claude`, только сверка хэшей): не даёт запушить рассинхронизированный `content-ru/`.
- Оба хука проверяют `$CI` и ничего не делают в GitHub Actions — деплой всегда собирает то, что уже закоммичено, без переводческих вызовов и без риска сломать пайплайн из-за недоступного `claude`.
- Включаются через `"postinstall": "git config core.hooksPath .githooks"` — сработает у любого при следующем `npm install`.

## UI-переключатель

`local-plugins/lang-switch/` — локальный плагин (source: `./local-plugins/lang-switch` в `quartz.config.yaml`, `layout: {position: left, priority: 32, group: toolbar}`, рядом с darkmode). Особенность: local-плагины у Quartz грузятся плоским `import()` без esbuild/tsup-шага, поэтому компонент — чистый `.ts` с `preact.h()` вместо JSX (JSX не пройдёт без трансформации).

Кнопка серверно рендерится одинаково в обоих деревьях (`href="/ru/"`, подпись «RU»); инлайн-скрипт на клиенте при каждой навигации (`nav`/`render` события) смотрит `location.pathname` и подставляет подпись/ссылку на тот же slug в другом дереве. Работает и в SPA-навигации Quartz (`enableSPA: true`), и при обычной загрузке страницы.

## Локальная разработка

- `npm run serve:all` — собирает оба дерева и раздаёт их одним статическим сервером на `:8081` (`/` и `/ru/`). В отличие от `npx quartz build --serve`, которая собирает только `content/` (то есть `/ru` всегда даст 404), эта команда явно строит оба.
- Без live-reload — после правок контента команду нужно перезапускать.

## Почему два отдельных `quartz build`, а не один — и стоит ли их распараллелить

**Почему не один билд.** У Quartz нет мультиязычного content-пайплайна (`quartz/i18n` переводит только статичные UI-строки компонентов, не заметки) — научить один билд рендерить два языка для одного и того же slug означало бы переписывать content-page/folder-page/tag-page эмиттеры, поисковый индекс и граф так, чтобы они знали про пары «слаг + язык». Это ядро фреймворка, а не конфигурация — несоразмерно большая работа при 74 заметках. Два независимых билда — по сути, «два сайта», и это самый дешёвый способ получить рабочую RU/EN-версию без переписывания Quartz.

**Что уже упрощено по сравнению с более тяжёлым вариантом.** Изначально рассматривался вариант с материализацией `content-en/` и `content-ru/` из общего кэша (чтобы «родной» язык каждого файла тоже проходил через кэш/пайплайн перевода). От этого отказались: `content/` и так уже является EN-деревом «как есть» — отдельно материализовывать его не нужно, генерируется только `content-ru/`. Это одна из двух директорий вместо трёх (`i18n/cache/` + `content-en/` + `content-ru/` → просто `content-ru/`).

**Распараллелить оба билда, чтобы ускорить сборку?** Проверил и **не стоит**: у `quartz build` есть один нескоуп-нутый файл кэша сборки — `.quartz-cache/transpiled-build.mjs`, в который эсбилд пишет результат **при каждом запуске** (`quartz/cli/handlers.js:336`, `outfile: cacheFile`), независимо от `-d`/`-o`. Два параллельных процесса `quartz build` в одной рабочей директории будут писать в один и тот же файл одновременно — гонка записи. Два тестовых прогона параллельно прошли без ошибок, но это везение по таймингу, а не гарантия: при параллельных билдах возможен редкий, трудно воспроизводимый сбой (один процесс читает наполовину записанный файл другого). Локальный/CI выигрыш по времени (сборки идут ~8–12с каждая, итого ~20с последовательно) не стоит риска нестабильного деплоя, поэтому оба билда оставлены последовательными — как в `serve-both.mjs`, так и в `deploy.yml`.

**Что ещё не стоит делать:**

- Хранить оба языка в одном md-файле (frontmatter-блоки/разделители на язык) — не убирает необходимость двух билдов на выходе, а ломает ограничение «`content/` не трогаем» (это единственный источник правды из внешнего репозитория).
- Коммитить готовый `public/ru` вместо сборки в CI — раздувает репозиторий сгенерированным HTML и рассинхронизируется с кодом компонентов при любом изменении вёрстки.

## Известные ограничения

- `content-ru/` не обновляется автоматически, если контент синкается только в CI (`sync-obsidian-notes.sh` в `deploy.yml`) без последующего локального коммита разработчика — `claude` CLI недоступен headless в GitHub Actions (OAuth-логин интерактивный). До следующего локального коммита `content-ru/` может показывать устаревший перевод; сайт при этом не ломается, просто РУ-версия конкретной заметки отстаёт.
- Статические ассеты (JS/CSS/шрифты) задваиваются между `public/` и `public/ru/` — оба билда независимо копируют одни и те же файлы. Не оптимизировано: объём небольшой (десятки KB на 74 заметки), а дедупликация потребовала бы постобработки вывода и была бы хрупкой.
